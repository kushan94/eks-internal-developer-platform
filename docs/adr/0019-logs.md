# ADR 0019: Logs for every service with Loki and Alloy

**Status:** Accepted (2026-11-13)

## Context
The platform had metrics and alerts but no logs beyond `kubectl logs`, which only shows pods that still exist, one at a time. When an alert fires for a pod that has since restarted, the logs that explain it are gone. Logs are the first thing a developer looks at, and production platforms collect them centrally.

## Decision
- **Loki in single-process mode** stores the logs.
  - On EKS it writes to an S3 bucket, `idp-logs-<account>`, from the bootstrap stack, so logs survive the nightly destroy. Loki reaches the bucket through a Pod Identity role limited to it.
  - On kind it uses its local disk.
  - Logs are kept for 7 days: Loki's compactor deletes older ones, and an S3 lifecycle rule catches anything it misses.
- **The chart's scaled-out defaults are off:** the memcached caches (which reserve 9 GiB), the gateway, the canary and the test pod.
- **Grafana Alloy runs on every node.**
  - It tails each container's log file and labels every line with `namespace`, `pod`, `container` and `service`.
  - `service` is the `backstage.io/kubernetes-id` pod label, the same one the dashboard and alerts use, so a service's logs include its in-cluster database.
  - It drops the file path label, which would start a new stream every time a container restarts.
- **Grafana gets Loki as a data source.** The `WebService` dashboard gains a logs panel for the selected service, so metrics and logs are on one page.
- **Testing:** `make test` checks that Alloy's pipeline parses. Loki's generated config passed `loki -verify-config` for both storage modes. On a throwaway kind cluster, a pod labelled like a `WebService` had all its lines in Loki under its `service` label.

## Alternatives considered
- **CloudWatch Logs with Fluent Bit:** nothing to run, but it doesn't work on kind, costs per GB ingested, and puts logs in a different tool from the metrics.
- **The ELK or OpenSearch stack:** full-text indexing, at many times Loki's memory. Loki only indexes labels, which suits finding a service's logs and then searching within them.
- **Alloy reading logs through the Kubernetes API:** no host mounts, but every line passes through the API server.

## Consequences
- **The logs bucket must exist before an EKS session,** so `make bootstrap` comes first. Otherwise Loki can't start, and the Cluster workflow waits for it.
- **Memory:** Loki asks for 256 MiB, and Alloy for 128 MiB on each node.
- **Only Kubernetes logs.** ECS services' logs stay in CloudWatch Logs.
- **One Loki replica.** Losing its pod pauses log collection until it restarts. Alloy buffers what it can meanwhile. A scaled-out Loki is the next step if logs become critical.
